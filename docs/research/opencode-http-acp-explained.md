# OpenCode HTTP and ACP: integration choices explained

Research date: 2026-10-01. This note answers the transport, standalone-deployment, request-separation, and wrapper questions. It records source inspection, not a live deployment test. The preprocessing proposal targets OpenCode **2.0.19**, commit `1fd016ef32286de9489b7b24f1029f52c49a27b3`. Public wrapper examples are separately pinned below; their API generations must not be assumed interchangeable.

## Summary

- The existing geo-report pipeline most closely resembles **A: direct native HTTP access**. Its normal clients connect to an externally managed server. That is a transport precedent, not a complete implementation of durable recovery, request ownership, or chat-history filtering.
- **B: a runtime-owned extraction broker using the existing ACP connection** fits the runtime's approved gateway plan. Python would call the broker's private HTTP API; it would not independently launch another ACP process.
- Standalone service deployment is compatible with either integration choice, but the current proposal explicitly restricts its owned launcher to development. Standalone production therefore needs an explicit deployment contract: a dedicated, externally supervised OpenCode server is the simplest default. Treating standalone production as supported is an adjustment to the proposal's scope.
- ACP is a standardized agent-client interaction protocol. Native HTTP is OpenCode's own server-control API. They reach the same engine; native HTTP exposes more engine-specific controls, not a more capable model.
- T3 Code's inspected public OpenCode adapter uses native HTTP and SSE. Zed uses ACP over stdio. OpenCode's own web UI uses native HTTP and SSE.

## 1. The basic model

OpenCode owns model/provider integration, agent execution, tools, permissions, session state, and output. A client supplies requests and consumes results. A client can be a terminal UI, web UI, editor, gateway, or headless service.

Two interfaces are relevant:

| Interface | Purpose | Actual OpenCode boundary |
| --- | --- | --- |
| Native HTTP API | Programmatically control an OpenCode server, including engine-specific session state and administration. | HTTP requests; event streams use server-sent events (SSE). The pinned server exposes `/api/...` and `/openapi.json`. |
| Agent Client Protocol (ACP) | Standardize interaction between coding agents and clients, reducing agent/editor-specific integrations. | At this pin, `opencode acp` exchanges newline-delimited JSON-RPC over stdin/stdout. It owns a private HTTP server internally. |

ACP's ordinary turn lifecycle is initialize → create/load session → prompt → streamed session updates and possible permission requests → prompt response with a stop reason. Cancellation is session-scoped. Sessions represent separate conversation contexts. ACP's capability negotiation determines which optional methods may be used. [1–3]

The pinned OpenCode ACP adapter advertises image and embedded-context prompts, session load/list/resume/fork/close/delete, model/effort/mode configuration, and usage updates. Thus claims that ACP cannot handle images, multiple sessions, model selection, or deletion would be incorrect for this pin. [4]

The important ownership detail is:

```text
ACP client
  → opencode acp (JSON-RPC over stdin/stdout)
      → private opencode serve (native HTTP)
          → configured model providers
```

Official documentation states: “The command starts a private OpenCode server for that ACP process” and “it does not expose an ACP network port.” The process supports multiple ACP sessions and ends when its client closes stdin. [3]

At the pinned version the child password is generated by its owner, overriding an inherited password. Its HTTP endpoint/password are not exported as a supported third-party ACP connection descriptor. A fresh `opencode acp` starts another server; it does not attach another client to the existing engine. [5]

## 2. What A and B change

### A: preprocessing directly calls the runtime-owned HTTP server

```text
Runtime gateway ─┐
                ├─ native HTTP → one runtime-owned OpenCode server
Preprocessing ──┘
```

The runtime explicitly provides connection details. Preprocessing's existing durable job store also tracks its model operations and session IDs. The runtime still needs ownership-aware cleanup after service loss and filtering of internal sessions from interactive history. Direct HTTP does not eliminate those responsibilities.

### B: preprocessing asks the runtime gateway to perform extraction

```text
Preprocessing → private extraction API → runtime gateway/broker
                                              ↓
                                       shared ACP connection
                                              ↓
                                        opencode acp
                                              ↓
                                   one private OpenCode server
```

The broker creates and classifies internal extraction sessions, dispatches their prompts, routes callbacks, handles cancellation, and retains minimal operation/session bindings. Preprocessing retains jobs and artifacts. These private broker routes are proposed application APIs, not standard ACP methods or existing OpenCode endpoints.

These choices combine two independent decisions: **who manages extraction session lifetime** and **which transport accesses the engine**. A broker could use native HTTP if the runtime chose to expose it. The current B specifies ACP to fit the approved gateway topology.

## 3. Comparison with the existing geo-report pipeline

Direct local inspection found two ordinary HTTP clients: the figure-description client and analysis model backend. Both create sessions and post messages through Python `urllib`; the analysis backend describes its dependency as an “externally managed `opencode serve`.” Neither ordinary client owns the server process.

Executable packaging and backend selectors call these clients, so this is wired application code rather than only a proposal. The old clients use `/session` and `/session/{id}/message`, with synchronous response extraction and mutation retries. They do not implement the proposed pinned-v2 API or its durable ownership/reconciliation policy. Fresh sessions and descriptive titles separate context, but do not provide caller authorization or chat-history exclusion.

A separate Dundas evaluation script deliberately owns a standalone server and cleans up sessions. That demonstrates an owned standalone topology; it is not the normal shared-runtime client and does not establish the proposed clean-HOME/XDG launcher behavior.

The MCP wrapper in geo-report exposes report-data tools to callers. It does not borrow OpenCode through ACP for extraction. MCP's tool-facing role should not be confused with ACP's agent-facing role.

## 4. Standalone deployment

“Standalone service” can mean **independent of the product runtime**, without meaning **independent of OpenCode**. The model-assisted path still needs an engine and configured provider credentials.

The simplest deployment is:

```text
External client → preprocessing service → dedicated OpenCode HTTP server
                                             → model provider
```

An operator can supervise the Python service and `opencode serve` through systemd or container process management. OpenCode documents foreground `serve` for “shared, always-on, or remote” hosts and supervision through systemd or Docker. [6] This does not require the product gateway or a browser. The HTTP extraction adapter is the same whether its server is shared by the runtime or dedicated to standalone preprocessing.

With A, runtime and standalone deployments use one extraction transport. With B, runtime deployment uses its broker client and standalone deployment uses the direct HTTP adapter. The parser/job/artifact behavior should remain the same across adapters.

The current proposal's isolated development launcher is not a standalone production launcher: it is explicitly development-only and refuses Fly activation. Supporting standalone production should therefore be stated separately, including ownership of the dedicated server and its configuration. Generalizing an owned launcher is possible, but externally supervised `serve` is simpler because process supervision need not be reimplemented inside the extraction service. This is a recommended scope clarification, not implemented behavior.

The proposal also requires engine readiness for native-format jobs. That is a chosen dependency contract, not an ACP or HTTP limitation: deterministic CSV/workbook parsing does not technically require a model session.

## 5. Separating service requests from user requests

ACP uses an agent-interaction model similar to an editor, but headless service clients are possible. The protocol does not require a visible chat card or a human to author every prompt. OpenCode's native UI can use HTTP instead.

Four distinct forms of separation matter:

1. **Context:** create a fresh extraction session instead of adding a prompt to a user's chat. Both interfaces support separate sessions.
2. **Routing and presentation:** maintain an authoritative operation/session ownership map, route callbacks by session ID, and exclude extraction IDs from interactive history. A title is only a display hint. A prompt `_meta` label is not enough: the pinned ACP adapter does not establish propagation of arbitrary client ownership metadata into durable native session records. [4]
3. **Execution policy:** select a dedicated `preprocessing` agent, controlled model, deny-all permissions, and a dedicated working location. These do not automatically remove global instructions or plugins already loaded by the shared server.
4. **Authority:** direct HTTP Basic credentials grant broad server access, not a per-preprocessing namespace. A narrow authenticated broker can enforce service-scoped operations at the application boundary. It is not OS-level isolation and does not make the model's global prompt context private by itself.

Under B, the runtime knows session ownership before routing extraction results and permission callbacks. Under A, it consumes the service's ownership projection for cleanup/history filtering. Both need intentional cancellation scoped to owned sessions. Starting another ACP process would yield a separate engine rather than solve sharing within this one.

## 6. Why the runtime plan chose ACP

Authenticated inspection of the approved plan at runtime commit `8585645b1d48a7a91901221ac5c879e1dba09cf3` found an actual HTTP-to-ACP revision history. Revision 2 used an HTTP/SSE adapter; revision 3 selected OpenCode 2.0 with ACP. [7]

The decisive passage is:

> “Those were the two gaps that ruled ACP out in 1.x. The broker is already an ACP client, so the rev-2 HTTP/SSE translation layer is not needed.”

The two gaps were specialist output forwarding and routing specialist permission requests through the root session. The plan uses OpenCode-specific child-session update capabilities to cover that behavior. Its HTTP fallback “costs about 2 days more than the ACP path.” These are project-specific reuse and effort arguments, not evidence that ACP exposes the larger API. [7]

The plan's probe concluded GO for ACP and kept HTTP as a fallback. It compares v2 ACP with previous v1 HTTP evidence; it does not establish a same-version head-to-head transport benchmark. Its accompanying status note says: “Nothing browser-facing has changed yet” and “The code that exists today is test code for the engine, not the new gateway.” Those statements apply to that inspected commit, not necessarily a later deployment. [8]

## 7. Why native HTTP is broader, and what ACP provides

The meaningful comparison is **native engine-control surface versus standardized agent-interaction surface**. HTTP itself is not intrinsically more expressive than JSON-RPC. ACP extensions can add capabilities, but an OpenCode-specific extension is no longer a portable guarantee for all ACP agents.

Pinned source establishes concrete differences: [4,9]

| Capability | Native OpenCode HTTP at 2.0.19 | Pinned OpenCode ACP adapter |
| --- | --- | --- |
| Text/image prompts, independent sessions, model/agent selection, cancellation, deletion | Supported. | Supported; some capabilities are negotiated. |
| Choose session ID before creation | `session.create` accepts optional `id`. | `newSession` calls native create without a caller-chosen ID. |
| Choose durable prompt ID | Native prompt accepts optional `id`. | Adapter generates the message ID internally. JSON-RPC request IDs are not native durable prompt IDs. |
| Apply session metadata and permissions at creation | Explicit native payload fields. | Not exposed as equivalent native creation fields by this adapter. |
| Inspect pending durable input and cancel a particular inbox item | Native inbox list/cancel endpoints. | No equivalent public method in this adapter. |
| Read message records and a durable per-session event cursor | Message endpoints and an experimental session-log endpoint. | Saved-message replay and live updates are exposed; no equivalent native cursor API in this adapter. |
| Engine-specific catalogs/configuration/debug controls | Native API groups. Some are experimental. | Selected configuration options and capabilities, not all native administration. |

Durable, caller-chosen IDs matter for extraction because the service can record them before sending a request and later reconcile an uncertain response. This is not an exactly-once guarantee for provider execution. Native prompt admission still requires result correlation; the HTTP prompt response is admission, not final model output.

ACP benefits:

- **Interoperability:** one client integration can support different compatible coding agents, similar to LSP for language servers. [1]
- **Standard interactive events:** text, reasoning, tools, plans, permissions, configuration changes, stop reasons, and cancellation do not need a separate UI integration for every engine. [2]
- **Bidirectional client participation:** clients can implement permission handling and optional filesystem/terminal capabilities.
- **Capability/version negotiation:** clients discover optional support rather than assuming all agents implement the same feature set.
- **Local subprocess lifecycle:** stdio makes editor-owned local agent startup straightforward. This is a convenience for that topology, not a complete standalone service or multi-tenant authorization solution.
- **Existing runtime reuse:** the inspected gateway already speaks ACP; its accepted 2.0 probe covers the specialist behavior it needs. [7]

For a headless extraction service deliberately standardized on OpenCode, portability to other coding agents is less valuable than it is for a multi-agent editor. Native IDs, durable readback, and a single standalone/runtime adapter therefore make A attractive, provided the runtime deliberately supplies its HTTP endpoint and the ownership hooks.

## 8. Wrapper examples

### T3 Code

Public `main` inspected at `148e6deea046658639aae9fef5b349781cec39d1`:

```text
T3 frontend → typed WebSocket requests → T3 backend/OpenCode adapter
                                             → native HTTP requests
                                             ← native SSE events
```

The runtime calls `createOpencodeClient({baseUrl, directory, ...})`, local startup arguments begin with `serve`, and the adapter calls `session.promptAsync` and `event.subscribe`. A configured `serverUrl` is marked externally owned; T3 need not launch that server. T3 translates native events into its own orchestration events. [10–12]

This source uses older `/session/...`-style SDK operations. The import name `@opencode-ai/sdk/v2` must not be mistaken for proof that it uses the proposal's OpenCode 2.0 `/api/...` contract. This research does not establish the T3 commit deployed in the current session.

### Zed

OpenCode's official configuration launches `opencode` with `args: ["acp"]`. Zed's inspected source at `74c134a3c12418cc095122fff938ef1c2504ae06` spawns the child with piped stdio, performs ACP capability/session negotiation, and routes session notifications to the matching thread. This is ACP at the wrapper-facing boundary even though OpenCode internally owns a native HTTP server. [3,13]

### OpenCode's own web UI

OpenCode source inspected at `0112a92c416f5ad833d96e7a8308441f0a875d94` builds native clients for the selected server and explicitly supports legacy and newer native event APIs. It uses HTTP/SSE, not ACP, for browser-to-engine operations. [14]

## Verification and limits

- **Decision:** direct source inspection and documentation lookup; no application tests warranted for a research-only addition.
- **Evidence:** local executable clients established direct HTTP usage; pinned 2.0.19 ACP implementation advertises session lifecycle/image support and internally calls native session methods; native schemas expose caller-chosen IDs, permission/metadata fields, and inbox/log controls. Authenticated GitHub API retrieval succeeded for both runtime documents at the specified commit. First-party wrapper sources establish transport choices.
- **Not established:** deployed runtime/T3 version, actual shared-engine request isolation, live cancellation/recovery behavior, memory or latency outcomes. No engine processes or provider calls were started.
- Some public documentation paths timed out or returned 404; successful official ACP/server pages and pinned source supplied the decisive evidence. Mutable documentation is supplementary to the pinned implementation.
