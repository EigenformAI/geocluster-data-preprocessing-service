# OpenCode 2.0.19 runtime-server integration

Research date: 2026-09-30. Scope: a production preprocessing **client of the already-owned runtime server**, not a new production engine. An isolated server is development-only. Desired incremental peak memory: <500 MB (decimal; approximately 476.8 MiB).

## Conclusions

1. **Yes: 2.0.19 supports standalone HTTP.** `opencode serve` is explicitly “Start the v2 API and web server.” ACP itself starts that server as a private child; ACP is not required for an HTTP client. The v2 HTTP interface is materially different from the still-accessible 1.x documentation. [S1–S5]
2. **Slight preference for a lean runtime-owned broker; direct HTTP is a viable simpler lifecycle option once the runtime deliberately supplies a supported endpoint.** Preallocated session/message IDs allow service-owned SQLite to be the single operation registry; no second broker database or queue is inherently required. The approved ACP-owned layout does not currently supply that HTTP endpoint to the gateway. Raw API credentials remain server-wide, not preprocessing-session authorization. [S6–S10,F1–F4]
3. **Session-specific agent/model selection and permission rules exist; session-specific removal of ambient global configuration is not established.** A preinstalled extraction agent plus deny-all session rules is useful, but does not prove that global instructions, plugins or project configuration cannot influence the model. A clean directory does not remove global discovery. The strict confidentiality requirement remains a runtime-owner prerequisite, not something a thin HTTP client can promise. [S6,S11–S15]
4. **No automatic client replay after uncertain dispatch.** More importantly, managed 2.0.19 servers themselves resume orphaned execution on restart. Source explicitly calls this recovery “at-least-once.” If the requirement is *no automatic provider continuation anywhere*, a broker alone cannot satisfy it against an unmodified managed server. [S4,S16]
5. **<500 MB incremental peak is plausible as a target, not verified.** Prior measurements include a separately owned ACP/server pair and exceed the target; they are not measurements of the proposed borrowed-server deployment. No provider calls, installs, server launches or new benchmarks were performed here.

Evidence labels below: **source-confirmed** means inspected pinned source; **prior observation** means retained local evidence, not rerun; **proposed** means an integration recommendation, not an existing runtime feature.

## Exact server entry points and authentication

**Source-confirmed:** [S1–S4]

| Item | 2.0.19 behavior |
| --- | --- |
| CLI | `opencode serve [--hostname H] [--port N] [--cors ORIGIN ...]`, optionally `--service` or `--stdio`. Combining those two flags errors. |
| Address | Default hostname `127.0.0.1`; ordinary serve with no explicit port tries 4096 and increments on address-in-use. Explicit `--port 0` requests an ephemeral port. Managed service can use saved service configuration. |
| Password | `OPENCODE_PASSWORD`, falling back to legacy `OPENCODE_SERVER_PASSWORD`; ordinary serve generates a random password if absent and prints it. Managed service instead uses its saved password or generates/persists one. Do not collect startup stdout as public logs. |
| HTTP auth | Basic username **`opencode`**. No `OPENCODE_SERVER_USERNAME` wiring appears in the inspected v2 launch path. Pairing-cookie/token and query-token mechanisms also exist; prefer an Authorization header, not credentials in URLs. |
| Readiness | Authenticated `GET /api/info`: version, PID, URLs, temporary path. During startup it returns 503 with `retry-after: 1`; ready is 200. This is server readiness, not proof of complete location catalogs. |
| Schema | `/openapi.json`, registered by the v2 HTTP API builder—not `/doc`. |

**ACP private HTTP reuse:** ACP's handler calls `Standalone.start()`; that spawns `serve --stdio --port 0`, sets a generated `OPENCODE_PASSWORD`, and receives `{url}` over child stdout. The parent holds the password, constructs a Basic-auth client, and owns a stdin lease. EOF ends the private server; ACP EOF exits its parent. Thus the child runs the same HTTP implementation, **but ACP stdio does not provide a public credential/endpoint-discovery contract for third-party clients**. Do not scrape processes, logs or environment to borrow it. A runtime owner may explicitly expose a broker/authorized endpoint; an ordinary already-owned `serve` endpoint is the straightforward HTTP integration. [S2–S4]

**Exact attachment limits (follow-up):** `Standalone` generates `randomBytes(32).toString("base64url")` and passes `env: { OPENCODE_PASSWORD: password }, extendEnv: true`; its explicit value overrides an inherited password. The child's first stdout line is parsed as `{url}`, with the password retained only in the parent's returned endpoint object. In `--stdio` mode the server removes both password environment names before tools inherit them and prints the URL descriptor, **not the password**. ACP's outward stdout carries ACP JSON-RPC, not this child descriptor. The command is declared `Spec.make("acp", { description: ... })` without attachment parameters, and its handler unconditionally calls `Standalone.start()` without reading `--server`, `--attach` or `--password`. **Neither attaching public `opencode acp` to an existing HTTP server nor exposing a known child URL/password through these flags/environment is supported by this pin.** An inherited `OPENCODE_PASSWORD` cannot force its child credential; no supported child-endpoint export environment variable was found in this path. Root/other commands' `--server` support must not be inferred to apply to ACP. [S1–S3,F5]

## Exact HTTP operation contract

These are **source-confirmed interfaces, not newly probed requests**. `{data: ...}` below is the wire envelope, which a generated SDK may unwrap. Location-scoped catalog/config queries use deep-object `location[directory]=<absolute-directory>`; session creation uses `location: {directory: ...}`. [S6,S7,S11,S17]

| Need | Exact interface and caveat |
| --- | --- |
| Create | `POST /api/session` accepts optional `id`, `title`, `agent`, `model`, `location`, `metadata`, `permissions`; returns `{data: SessionInfo}`. Save the operation→session association **before prompting**. |
| Select agent | At creation, `agent: "preprocessing"`; later `POST /api/session/:sessionID/agent` with `{agent}` returns no content. This selects a registered agent; it does not install a private agent definition. |
| Select model | At creation, or `POST /api/session/:sessionID/model` with `{model: {providerID, id, variant?}}`. **`id`, not 1.x `modelID`; variant is inside model.** |
| Prompt | `POST /api/session/:sessionID/prompt` with `{id?, text, files?, metadata?, delivery?, resume?}`. Returns `{data: SessionInbox.User}`: durable admission, **not final assistant output**. `resume: false` admits without scheduling execution. |
| Images | `files: [{uri: "data:image/png;base64,...", name: "page.png"}]`; ACP's image conversion feeds precisely this HTTP representation. No 1.x `parts` array. Prefer bounded inline data from approved staged bytes; reject arbitrary file/HTTP URIs supplied by extracted content. |
| Inspect result | `GET /api/session/:sessionID`; paginated `GET /api/session/:sessionID/message?order=asc&limit=200`, then returned cursors; one message at `GET /api/session/:sessionID/message/:messageID`. Message-list response is `{data, cursor}`. |
| Completion | Messages include `type: "idle"`, outcome `succeeded`, `failed` or `interrupted`; assistant records have content, optional finish/error and timestamps. Experimental `POST /api/experimental/session/:sessionID/wait` waits for idle and returns no content; idle alone is not successful extraction. Correlate the admitted input and terminal turn, then validate output. |
| Live events | `GET /api/event` is SSE **across all locations**, “Volatile by contract”; disconnects miss events and slow consumers can overflow. Do not forward this raw stream to preprocessing or browsers. |
| Durable events | Experimental `GET /api/experimental/session/:sessionID/log?after=<seq>&follow=true` reads after an exclusive session sequence and follows live events. Broker authorization still required. Persist a cursor; reconcile through messages/inbox after disconnect. |
| Interrupt | `POST /api/session/:sessionID/interrupt` returns `{interrupted: boolean}`; optional query `resume=true` resumes selected pending work, so omit it for cancellation. “Owned by this OpenCode process” means engine execution ownership, **not caller authorization**. |
| Pending inputs | `GET /api/session/:sessionID/inbox`; `DELETE /api/session/:sessionID/inbox/:inboxID` cancels an undelivered item, unavailable items being a no-op. Interrupting execution is not evidence that every queued input was removed. |
| Delete | `DELETE /api/session/:sessionID`, no-content response, deletes session **and children**. Guard the whole owned subtree. ACP `session/close` interrupts/detaches; it is not history deletion. Neither operation proves deletion at a provider. |
| Catalog/config | `GET /api/agent`, `/api/agent/:agentID`, `/api/model`, `/api/model/default` return location/data envelopes. `GET /api/config` returns raw ordered configuration documents/discovery sources, not a sanitized client profile. |
| Global mutations | `PATCH /api/experimental/config` is global; its pinned patch schema supports `shell` only, **not arbitrary per-job agents/models**. `POST /api/location/reload` rebuilds **every loaded location**. Neither belongs in the per-job path. |

Prompt/image/model shapes: [S6,S11,S17,S18]. Result/event shapes: [S8,S19,S20].

**Usage:** assistant messages carry optional `tokens`, `cost`, `model`, `finish`, `rawFinish`, `error`, `retry`; compaction can carry its own usage. Preserve absent values as unknown. Store evidence per message/attempt; do not add overlapping session and turn totals. These are runtime-reported accounting and selected-model records, not a verified billing ledger or proof of the provider's actual routed model. ACP separately emits prompt usage and session `usage_update`; its latter cost comes from session info. [S19,S21]

## No-tools agent and configuration isolation

**Confirmed selection:** a session may select a pre-registered extraction agent and supply `permissions: [{action: "*", resource: "*", effect: "deny"}]`. Native configuration uses plural `agents`, `permissions`, `plugins`; agent records expose system text, permissions and optional step limit. There is no inline session-create field for an arbitrary isolated agent/config document. **Deny-all permissions are not demonstrated here to remove every tool definition, plugin hook or ambient instruction from model context.** Exact effective permission precedence and adversarial behavior on the shared deployment still require verification. [S6,S12,S15]

**Discovery and environment are server-side, not client-side:** [S4,S13,S14]

- Server launch accepts `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG` (file), `OPENCODE_CONFIG_CONTENT`; project discovery is disabled by `OPENCODE_CONFIG_PROJECT_DISABLE` or legacy `OPENCODE_DISABLE_PROJECT_CONFIG` (truthy `1`/`true`). Models can be controlled through `OPENCODE_MODELS_URL`, `OPENCODE_MODELS_PATH`, `OPENCODE_DISABLE_MODELS_FETCH`.
- Effective configuration loads well-known provider sources, global directory, explicit file, direct project files, project `.opencode` sources and finally inline content. Compatibility discovery includes home/project `.claude` and `.agents`. Inline content is an overlay, **not a sandbox**.
- Core configuration and instruction-discovery services have a `global: false` composition option. The inspected CLI/server routes wiring passes **project**, not global; **no supported CLI environment switch for disabling all global discovery was established**. Do not invent `OPENCODE_DISABLE_GLOBAL_CONFIG`.
- A development server can use clean HOME/XDG directories, explicit configuration, no ambient credentials and project discovery disabled. This does not describe the existing production server. Changing the preprocessing client's environment cannot change the already-running server's discovery policy.
- Session environment replacement exists for shell commands; it is not a session-specific server credential/configuration sandbox. [S6]

**Confidentiality consequence:** deny tools *before dispatch*, but also prevent sensitive ambient text entering the provider prompt. Selecting a clean workspace, refusing arbitrary URI attachments and withholding raw config/events are necessary but insufficient when the engine still loads global instructions/plugins. A broker cannot redact secrets already supplied to the model. Production needs runtime-owner evidence of a genuinely restricted extraction context (or a runtime-owned isolation facility). If that is unavailable, model-assisted preprocessing must remain disabled; native-only extraction is the independently available path. Do not solve this by silently launching a preprocessing-owned production engine.

## Cold readiness and restart hazards

**Source-confirmed catalog race:** ACP caches one catalog promise per exact `cwd` string. Its five-second readiness loop returns on **any** enabled default model plus visible primary agent, not specifically `preprocessing`. `/api/model` explicitly warns that its snapshot “may precede initial plugin settlement.” Server-ready therefore does not imply extraction-agent-ready. [S11,S21]

**Prior local observation, not rerun:** cold catalogs were observed as empty → built-ins → configured preprocessing agent. Removing `opencode.agent` and `opencode.plan` registrations made the isolated development catalog expose only preprocessing; three catalog-only tests assert that result and selection round trips. This is **not** a suitable global change to a shared interactive server. The retained probe report records passing synthetic text/image/scoped-cancel/reuse, but does not establish shared-server confidentiality. [L2,L3]

**Proposed HTTP readiness:** use one canonical, trusted location; verify exact server version, then poll for the required agent, its expected properties, and exact enabled model/variant/image capability. Read back session selection before admission. Fail on missing/changed policy; never fall back to `build`, `plan`, a different model or a newly owned engine. HTTP avoids ACP's cached catalog but does not eliminate asynchronous initialization or configuration changes between reads.

**Restart is a stronger concern than transport retry:** managed-server boot calls `resumeSuspendedSessions`. The pinned implementation says “Recovery is at-least-once: local coordination prevents concurrent drains, not repeated external side effects after a crash,” and injects a continuation instruction; default maximum resume attempts is ten per turn. Ordinary unregistered servers do not run this sweep, including the approved ACP-owned `serve --stdio` child. Verify deployment matches that approved launch mode. A client must mark uncertain requests unknown, retain IDs and reconcile; it must not create replacement sessions/prompts automatically. If switching to managed service and requiring no automatic provider continuation, require a runtime-owned recovery policy before production admission; the inspected public session API exposes no per-session no-recovery switch. [S4,S16]

## Follow-up: preallocated identity, duplicate admission and cleanup

### Session identity can be durable before the first HTTP request

**Source-confirmed:** the HTTP handler forwards `ctx.payload.id` to core `Session.create`. `SessionID` validation is only a string starting with **`"ses"`**—not a UUID/length/full-pattern check. The native generator emits `ses_` plus a 26-character suffix: 12 hex characters from the descending timestamp/counter encoding, followed by 14 alphanumeric random characters. Message ID validation requires **`"msg_"`**; native message IDs use the corresponding ascending suffix. A proposed service allocator can use a cryptographically random `ses_...`/`msg_...` value satisfying the schema (for example UUID-derived); matching the native sortable format is optional and only needed if relying on its ordering. Do not use predictable job titles as IDs. [F1,S19]

Core creation is **first existing session wins**, not a duplicate-ID conflict or overwrite:

```ts
const sessionID = input.id ?? SessionSchema.ID.create()
const recorded = yield* store.get(sessionID)
if (recorded) return recorded
```

The projector inserts with `.onConflictDoNothing()`; concurrent creation losing the projection race is caught as `SessionAlreadyProjected`, then returns the existing session. Conflicting creation payloads do **not** update the existing model, directory, permissions or metadata, nor trigger a documented 409. The client must verify the returned/retrieved identity and expected fields before use. This code supports safe duplicate *creation* while the identity remains present; it is not permanent idempotency after deletion and not caller authorization. [F2]

**Consequence:** commit `(operation, generation, sessionID, messageID, expected location/policy, state=prepared)` to service SQLite **before** `POST /api/session`. A lost acknowledgement can be reconciled with `GET /api/session/:id`; there is no inherently unreachable, server-minted prepare orphan on this HTTP path. Retain the prepared row/cleanup manifest until settlement. A 404 while the original create is still in flight is not proof it will never arrive: fence further sends, retain reconciliation responsibility, and do not retire the row on one negative read. The API has no reservation/tombstone preventing a late create after a delete. Retrying creation, if deliberately allowed before any prompt, must use the same ID; this recommendation does not authorize automatic prompt replay. [F2]

### Prompt IDs are first-admission-wins, not “all duplicates return 409”

`Session.prompt` first calls `admission.reconcile({id, sessionID, type: "user", delivery})`. Reconcile searches the inbox, then projected messages. Its source comment is **“First admission wins for matching Session and type, without preparing a new payload.”** Same ID, same session and same user type returns the original payload even if newly supplied text/files differ. A record belonging to a different session/type (or an incompatible durable record) raises `LifecycleConflict`, mapped through `PromptConflictError` to HTTP **409** with “Prompt message ID conflicts with an existing durable record”. [F3]

**Do not turn that into an exactly-once provider guarantee.** Even on a matching duplicate, the prompt method still calls `execution.wake(sessionID)` unless `resume === false`. Durable input deduplication is not a permanent execution tombstone; cleanup/cancellation can remove records, and managed restart recovery is separately at-least-once. After a lost prompt acknowledgement, query the known inbox/message ID and terminal history; do not resend, change the ID or recreate a deleted session automatically. An absent record does not by itself prove non-dispatch. Persist a local terminal/tombstone record beyond engine-history deletion. [F3,S16]

**Client retry facts:** the pinned Promise SDK's generated `execute` calls `fetch` once and wraps a thrown transport error; `request` performs one `execute`, with no retry loop/options. The higher-level Promise client wraps events/RPC, not `session.prompt`; its shared event stream finishes on failure rather than replaying prompts. This establishes the inspected default Promise HTTP path only—not custom fetch wrappers, proxies, another SDK, or the engine's provider retry behavior. Proposed direct transport must have mutation retries disabled and no redirects that resubmit unexpectedly; reconnect/read retries must remain separate from admission. [F4]

### Delete cleans session resources, but is not complete or permanent disposal

Core `Session.remove` does more than delete database history, in this order: get the session, interrupt execution, await idle, `transport.close(sessionID)`, recursively remove children, clear session environment, publish `SessionEvent.Deleted`, and `bus.remove(sessionID)`. `SessionModelTransport.close` explicitly calls `states.delete(sessionID)` and closes the live channel. The deletion projector removes the session row; message, inbox and instruction-state tables have cascading session foreign keys. Thus **some runtime state is evicted as well as persisted history**. It does not promise immediate RSS return, removal of every plugin cache, snapshot/blob/file cleanup, secure erasure or provider-side deletion. [F2,F6]

Clean terminal deletion does not itself submit a prompt; its path contains no wake/resume. Under exclusive ownership with no in-flight mutation, it is appropriate after persisting output/usage and terminal evidence. But deletion is **not a concurrency fence or exactly-once guarantee**: fence writers first; finish cancellation/settlement; retain local tombstones; never reuse the ID. A lost delete acknowledgement can be followed by `GET` and an owned-ID cleanup retry (404 means absent at that observation), rather than recreating anything. Unexpected children require ownership validation before using recursive deletion. [F2,F3]

**Location resources are separate.** Healthy location graphs are cached with **`idleTimeToLive: Duration.infinity`**. Session deletion does not invalidate that graph or ACP's per-`cwd` catalog map. ACP `session/close` detaches session state; `session/delete` removes and detaches it, but neither removes its cached catalog. A fresh session is not a fresh location. [F7,S21]

There **is** a registered targeted HTTP endpoint: **`DELETE /api/debug/location?location[directory]=<directory>`**, 204, described as “Dispose the requested location's cached services so its next use boots them fresh.” The handler calls `locations.invalidate(requestRef(ctx.request))`. Invalidation detaches routing and closes location interactions; running steps can retain their borrowed graph until a boundary. Therefore this is **targeted debug eviction, not permanent disposal**, not an engine-wide memory reset, and not proof that active work has terminated. It does not clear an external ACP process's catalog map. Use only after all sessions/requests using a preprocessing-exclusive location settle; never evict a shared chat location per job. No permanent public session/location tombstone API was established. Global `/api/location/reload` is unnecessary for this targeted operation. [F7,F8]

## Both production options, without a second queue

These are **proposals**, not implemented runtime features. Both retain the confidentiality prerequisites above, explicit agent/model selection, no global configuration mutation, scoped cancellation, uncertain-outcome handling and no automatic client replay. Process sandbox design is outside this follow-up.

### A. Direct HTTP + service SQLite + small runtime-supervised lease manifest

**When preferable:** the runtime deliberately provides an authenticated endpoint for its existing server, and the service can be trusted with that authority. Caller-chosen IDs eliminate the strongest argument for a duplicate broker registry.

1. **One authoritative ledger:** the preprocessing service owns operation state in SQLite and allocates both IDs before creation. Use a small bounded manifest under a runtime-approved private root containing lease generation, engine generation, location and owned IDs/cleanup state—no prompts, images or credentials. It is a cleanup projection of SQLite, not another queue or independently editable operation database.
2. **Publish before create:** commit the prepared SQLite row, then durably publish/acknowledge the manifest before any create request. Crash between these steps leaves no remote work. The runtime supervisor only watches this known root, with a startup rescan; it does not discover ownership by scanning all engine sessions. Surplus stale manifest entries are reconciled harmlessly by ID, not discarded on timeout alone.
3. **Dispatch once:** create/read back expected session identity, persist `dispatching` before sending the one prompt with the preallocated message ID, then reconcile admission/result. One fresh session per bounded operation simplifies correlation. Never load production chat history. Filter output to the required text/usage records; do not consume raw global events or configuration as extraction output.
4. **Owner loss:** runtime supervision must revoke/fence the service's ability to issue further requests before cleaning manifest-owned work; a heartbeat expiry alone is not proof a paused writer is dead. Cancel owned pending inputs, interrupt, wait/reconcile local terminal evidence, then delete according to retention policy. The watcher needs no prompt queue. It records/retains cleanup-pending evidence while the engine is unavailable. Local settlement does not prove remote provider cancellation.
5. **History and memory:** retain local results/usage and deduplication tombstones; delete engine sessions after terminal settlement. Reuse one canonical preprocessing-only location, or evict that exclusive location at quiescence through the debug route. Creating many per-job locations without eviction accumulates indefinitely cached graphs.
6. **Generation changes:** manifest/ledger engine generation comes from runtime ownership, not PID alone. Restart reconciliation never reissues a prompt. For the approved private `serve --stdio` child, the managed-service recovery sweep is not installed; changing to `serve --service` would change that property and must not be an incidental deployment choice. [S3,S4,S16]

**Remaining cost:** SQLite↔manifest ordering, supervisor fencing, UI/history filtering and endpoint handoff must still be defined. A small read-only ownership lookup/projection for the runtime's history filters may be simpler than a second registry. This design removes unaddressable create-ack orphans but cannot eliminate every in-flight-request or outage cleanup window. It is not available merely by setting `OPENCODE_SERVER_URL` while retaining the approved unmodified ACP-owned startup.

### B. Lean runtime broker, using existing ownership state

**When preferable:** keep the approved single-ACP runtime and centralize its lifecycle, history filtering and credentials. Add a narrow extraction capability to that runtime, not a new engine, scheduler or general-purpose HTTP proxy.

The broker needs only prepare/bind, dispatch-once, inspect, cancel/settle and release/delete semantics. The preprocessing SQLite remains authoritative for job/results; reuse the runtime's existing session ownership record for the engine binding if it has one. Otherwise add a minimal operation→session/generation binding—not a second copy of the job state machine. Persist the binding before authorizing a prompt; a lost bind acknowledgement leaves a known unprompted runtime-owned session that can be cleaned by operation identity. The runtime fences a dead client, filters internal histories/events and performs cleanup without granting raw engine authority to the service. Both layers must agree which one alone may dispatch; do not run two independent retry loops.

**Important ACP limitation:** upstream `newSession` calls HTTP `session.create` internally without a caller-provided ID, and its outward request accepts the ACP cwd/MCP fields, not the HTTP `id`. Therefore the HTTP preallocation proof does not automatically apply to an unmodified ACP broker. Persist a prepare intent and bind the returned ID before prompting; the narrower runtime-crash-before-binding window still needs a runtime-owned orphan policy (for example its exclusively controlled extraction location), or an explicit runtime/upstream change enabling preallocated IDs. Broker marketing must not hide that window. Likewise, targeted HTTP debug eviction is not supplied by public ACP; adding it requires an intentional owner-side integration, not discovering the private credential. [S21,F5,F8]

**Trade-off and decision:** lean slightly toward the broker **for the approved ACP ownership topology**, because lifecycle/history routing is already the runtime's responsibility. Prefer direct HTTP if supported endpoint handoff plus the existing supervisor/manifest can deliver the same ownership and cleanup behavior with fewer moving parts. A broker using HTTP faces the same endpoint prerequisite as direct HTTP; a broker using ACP avoids that prerequisite but retains ACP's binding/catalog limitations. A runtime-owned bridge/custom composition or owner-started `serve --stdio` with a known credential can be designed explicitly, but **upstream `opencode acp --server` is not that bridge**, and starting a second production engine is not an acceptable shortcut. Neither option requires completion of the entire gateway migration; both require a small explicit runtime contract.

## Memory evidence and remaining acceptance gates

**Prior observations inspected directly:** retained JSON reports give map peak sampled process-tree PSS **560,944,128 bytes (534.96 MiB)** and manifest **531,181,568 bytes (506.57 MiB)**. They include launcher, coordinator, parser, guardian, ACP and private server. The map peak sample alone attributes 81,187,840 bytes PSS to ACP and 377,141,248 to its server. The historical idle service-only observation is 48.56 MiB. Sampling can miss peaks; the shared cgroup was explicitly nonexclusive. [L4,L5]

These observations support avoiding a duplicate engine, **not subtracting those two processes and claiming a production peak**. The existing server will consume additional memory for images, sessions, token buffers and retained history; shared mappings, concurrent chat work, base64/JSON copies and parser peaks make simple subtraction invalid. Proposed acceptance measurement: baseline and incremental cgroup/process memory on the real shared deployment, cold and warm catalog paths, largest supported input and agreed concurrency, including server growth and post-job retention. Keep payload/output/concurrency limits operator-visible and configurable; confidentiality and ownership boundaries are strict, while <500 MB is a target until measured.

Unresolved gates: actual deployed version versus the parent-confirmed approved topology; explicit endpoint handoff or ACP broker contract; effective no-tools and ambient-context isolation; scoped cancellation/cleanup and lease fencing under disconnects; bounded incremental peak and interactive latency. ID deduplication and targeted debug eviction are source-confirmed, not new runtime probes. None of the remaining deployment guarantees should be inferred from the isolated ACP probe.
